## Architecture

- `project.godot` — autoloads `GameState`, `DialogueManager`, `Controls`, `HelpOverlay` (see below), renderer set to gl_compatibility for headless-friendliness, `[display]` forces windowed mode at 720x480.
- **Control scheme (2026-09-03, user-specified)**: arrow keys move; `Z` confirms/interacts/talks/attacks; `X` cancels/runs/closes; `H` toggles the help overlay; `Esc` pauses. `scripts/controls.gd` (autoload `Controls`) adds `KEY_Z`/`KEY_X` to the built-in `ui_accept`/`ui_cancel` actions in `_ready()`, so every `Button`-based screen (dialogue choices, pause menu, battle, title menu) gets Z/X for free through Godot's own focus system — engine-default Enter/Space/arrow-key bindings are left in place alongside them, not stripped. Raw (non-Button) input checks — `npc.gd` interact, `dialogue_box.gd` continue — check `KEY_Z`/`KEY_X` directly. `Controls.is_help_open` is a flag other scripts gate on exactly like they already gate on `DialogueManager.is_active`. `A`/`S`/`D` are now used as battle-only shortcuts (see below); `C` is still unassigned.
- `scenes/HelpOverlay.tscn` / `scripts/help_overlay.gd` (autoload `HelpOverlay`) — a `CanvasLayer` at `layer = 50` so it draws above whatever scene is active without per-scene wiring (same reasoning as `GameState`/`DialogueManager` surviving scene changes). `H` toggles it, `Esc` closes it (and consumes the event so pause doesn't also open that same press).
- `scenes/Main.tscn` (script `scripts/main.gd`) — the playable scene, now multi-room. `_load_map(map_id)` clears everything the previous room spawned (tracked in `_spawned_nodes`) then renders `data/maps/<map_id>.txt`, loads `data/maps/<map_id>.doors.json`, and spawns that room's NPCs. **No scene editing needed to add an NPC or a room.**
- **ASCII rendering convention**: every visible entity (map tile, player, NPC) is a `Label` control sized to exactly one `TILE_SIZE` (24px) cell, showing one character, `horizontal_alignment`/`vertical_alignment` centered. This is why no monospace font is needed — alignment comes from the fixed-size cell, not from glyph width, so Godot's default font is fine. `main.gd`'s `TILE_SIZE`/`TILE_COLORS`/`tile_center()` are the shared constants; keep any new tile-placing code consistent with them (use `tile_center(col, row)` to position entities on the grid, don't hand-compute pixel offsets).
- `data/maps/*.txt` — plain-text ASCII maps, one line per row, one character per column, all rows equal length. Glyphs: `#` wall, `T` tree (both solid — see collision below), `.` floor, `~` water accent, `+` door (walkable — see below), `o`/`R` shrine/relic decoration (walkable). Any glyph in `WALL_GLYPHS` also gets a `StaticBody2D` + `RectangleShape2D` covering its tile — add new solid glyphs there, not by special-casing `"#"` elsewhere.
- `data/maps/<id>.doors.json` (optional sibling of `<id>.txt`) — array of `{"position": [col, row], "target_map": "<id>", "target_spawn": [col, row]}`, optionally with `"requires_flag": "<name>"` (door is inert until that `GameState` flag is set — see `data/maps/cave_depths.doors.json` for a working example). `main.gd._check_door_crossing()` runs every frame (same cadence as the existing player-position sync) and swaps rooms in place — no `change_scene_to_file`, which stays reserved for Title/Battle transitions. **When adding a door, never make `target_spawn` land on a door tile** (including the same one) — it'll immediately re-trigger. Land one tile inside the room instead.
- `scenes/Player.tscn` / `scripts/player.gd` — top-down arrow-key movement (`CharacterBody2D`), frozen while `DialogueManager.is_active` or `Controls.is_help_open`. Visual is a `Label` showing `@`.
- `scenes/NPC.tscn` / `scripts/npc.gd` — reusable NPC: `Area2D` proximity detection, "!" prompt, `Z` to talk. Exported fields (`npc_name`, `dialogue_path`, `portrait_color`, `glyph`) are set programmatically by `main.gd` from the NPC's JSON file, not hand-edited in the scene. Visual is a `Label` showing the one-character `glyph`, tinted `portrait_color`. **Note**: NPCs have a real `CollisionShape2D` and do physically block the player (this is how proximity detection coexists with talk-range) — keep new rooms' walkable areas wide enough that an NPC placement can't accidentally wall off a path.
- `scripts/game_state.gd` — autoload singleton (`GameState`). Holds `flags: Dictionary`, `current_map` (which room to load), `player_position`, and `party_hp`/`party_rp` (`Dictionary`, keyed by party-member id — see the battle system bullet below), persisted immediately to `user://save.json` on every `save_game()` call. `reset_new_game()` resets in-memory state to fresh-game defaults without touching the save file — used by the title screen's "New Game".
- `scripts/dialogue_manager.gd` — autoload singleton. Loads a dialogue JSON graph, walks nodes, tracks `is_active`. A node with `"set_flag": "name"` sets that `GameState` flag when shown. A choice with `"requires_flag": "name"` / `"requires_not_flag": "name"` is filtered out of the rendered choice list unless the condition holds — both can be present on the same choice (AND) (see `dialogues/elder.json`/`dialogues/cave_guard.json` for working examples). A node with `"start_battle": "<enemy_id>"` can also carry `"victory_flag": "<name>"` — set via `GameState.pending_victory_flag` and turned into a real flag by `battle.gd` if the player wins (see `dialogues/cave_guardian.json`).
- **Battle system (2026-09-04, party-based D&D-5e-lite rewrite — see the "Battle system rewritten" Done entry for the full design writeup)**: `scenes/Battle.tscn`/`scripts/battle.gd` runs a fixed 3-person party (`data/party/*.json`) against one enemy (`data/enemies/<id>.json`, named by `GameState.pending_battle_enemy`, same trigger mechanism as before). `scripts/combatant_stats.gd`/`scripts/skill.gd` (`class_name CombatantStats`/`Skill`, plain `RefCounted`, built via `from_dict()`) hold the D&D-5e SRD-lite math (ability scores, AC, d20 attack rolls, save DCs, hit-die HP); `scripts/dice.gd` (autoload `Dice`) rolls dice-string expressions; `scripts/kaomoji.gd` (autoload `Kaomoji`) maps battle-state keys to kaomoji glyphs for `scenes/CombatantView.tscn`. `scenes/ActionMenu.tscn`/`scripts/action_menu.gd` drives the Attack/Skill/Defend/Run menu (`A`/`S`/`D` jump straight to those three from the top level). Both `data/party/*.json` and `data/enemies/*.json` use the same `CombatantStats` JSON schema, following this project's `field`/`field_zh` bilingual convention throughout.
- **Item/equipment system (2026-09-04 — see the Done entry below for the full writeup, and "How to add an item"/"How to add a world item" above)**: `scripts/item_database.gd` (autoload `ItemDB`) indexes `data/items/*.json`. `GameState.inventory` (shared consumables+owned equipment) and `GameState.equipment` (per party-member id) persist in the save file; battle applies equipment fresh each fight (`battle.gd._apply_equipment`) onto `CombatantStats`' `equip_attack_bonus`/`equip_damage_bonus`/`equip_ac_bonus` fields, and its Item action (`battle.gd._do_item`, `I` shortcut) consumes a `data/items/*.json` entry. World pickups are `scenes/WorldItem.tscn`/`scripts/world_item.gd`, spawned from `data/map_items/*.json` the same way NPCs spawn from `data/npcs/*.json`.
- **Roaming encounters (2026-09-04)**: `main.gd._check_random_encounter()` reads an optional `data/maps/<id>.encounters.json` for a per-tile chance/enemy-pool (Sunken Grove's tall grass); `scenes/RoamingMonster.tscn`/`scripts/roaming_monster.gd`, spawned from an optional `data/maps/<id>.monsters.json` (`main.gd._spawn_monsters`), chases the player on sight and forces a battle on contact (Ember Hollow). Both funnel into the same `GameState.pending_battle_enemy` + deferred-scene-change path NPC battles already use.
- `scenes/DialogueBox.tscn` / `scripts/dialogue_box.gd` — bottom-of-screen UI (raised/enlarged 2026-09-03 to stop it crowding the window's bottom edge when choices appear). Reveals `text` with a typewriter effect (`RichTextLabel.visible_ratio` animated via `Tween`, speed = `SECONDS_PER_CHARACTER`); pressing `Z` while typing calls `Tween.custom_step()` to skip straight to full text instead of advancing. Once fully revealed, renders one `Button` per (flag-filtered) choice, or a "press Z" continue prompt if there are none.

### How to add a new NPC (the workflow the user asked for)

1. Write a dialogue graph: `dialogues/<name>.json`. Shape:
   ```json
   {
     "start": "greet",
     "nodes": {
       "greet": { "speaker": "Name", "text": "...", "choices": [
         { "text": "option A", "next": "node_a" },
         { "text": "option B", "next": "node_b" }
       ]},
       "node_a": { "speaker": "Name", "text": "...", "next": "end" },
       "end": { "speaker": "", "text": "", "end": true }
     }
   }
   ```
   Nodes with `choices` branch; nodes with `next` (and no choices) auto-advance on `Z`; a node with `"end": true` (or a dangling `next`) closes the dialogue box.
2. Write an NPC definition: `data/npcs/<name>.json`:
   ```json
   { "id": "name", "name": "Display Name", "glyph": "X", "position": [x, y],
     "color": [r, g, b, a], "map": "<map_id>", "dialogue": "res://dialogues/<name>.json" }
   ```
   `glyph` is the single character shown on the map (ASCII style — see Project spec). `map` is which room this NPC spawns in (defaults to `"village"` if omitted — all pre-existing NPCs still say so explicitly). `position` should land on a tile center: `[(col + 0.5) * 24, (row + 0.5) * 24]` for column/row in that room's map file.
3. Run the headless smoke test above. That's it — no `.tscn` editing.

### How to add a new room

1. Write `data/maps/<id>.txt` (ASCII grid, as above).
2. Optionally write `data/maps/<id>.doors.json` for its exits (see above) — a room with no doors file is just a dead end.
3. Add NPCs scoped to it via `"map": "<id>"` in their `data/npcs/*.json` (see above).
4. Optionally add world items (`data/map_items/*.json`, see below), a per-tile random-encounter config (`data/maps/<id>.encounters.json`), and/or fixed roaming monsters (`data/maps/<id>.monsters.json`) — see their own sections below.
5. No `.tscn` editing, no code changes — `main.gd` discovers everything from these data files.

### How to add a world item (chest/barrel/bottle/etc.)

Write `data/map_items/<name>.json`:
```json
{ "id": "<unique_id>", "map": "<map_id>", "position": [x, y],
  "glyph": "=", "color": [r, g, b, a], "item_id": "<res://data/items/ id>", "quantity": 1 }
```
`position` should land on a tile center (same `(col+0.5)*24` math as NPCs). Walk up and press `Z` to collect — it's gone permanently afterward (a `GameState` flag defaulting to `world_item_<id>_taken`, overridable via an optional `"collected_flag"` field). See `scripts/world_item.gd`/`scenes/WorldItem.tscn`.

### How to add an item (consumable or equipment)

Write `data/items/<id>.json` — `"type"` is `"consumable"` (needs `"effect"`: `heal`/`restore_rp`/`damage`/`buff_attack`/`buff_defense`, `"target"`: `ally`/`enemy`/`self`, and `"amount_dice"` for heal/damage or `"amount"` for the RP/buff effects) or `"equipment"` (needs `"slot"`: `weapon`/`armor`, plus `attack_bonus`/`damage_bonus`/`weapon_dice`/`weapon_name(_zh)`/`weapon_symbol` for a weapon or `ac_bonus` for armor). See `data/items/*.json` for working examples of each. `ItemDB` (autoload) picks it up automatically — no code changes. To let players find it in the world, add a `data/map_items/*.json` entry (above); to make it a starting/quest reward, `GameState.add_item(id, count)` from wherever that reward is granted.

### How to add a random/roaming encounter to a room

Two independent mechanisms, either or both per room:
- **Per-tile chance** (see Sunken Grove): write `data/maps/<id>.encounters.json`: `{"glyphs": ["<tile char(s)>"], "chance": 0.15, "enemies": ["<enemy id>", ...]}`. Use a distinct glyph (this project uses `,` for tall grass; add a `TILE_COLORS` entry in `main.gd` for it if it needs its own tint) somewhere in the room's `.txt`. Checked once per newly-entered tile, not every frame — see `main.gd._check_random_encounter()`.
- **Chasing monsters** (see Ember Hollow): write `data/maps/<id>.monsters.json`, an array of `{"position": [x, y], "enemy_id": "<id>", "glyph": "<char>", "color": [r,g,b,a], "speed": 70, "chase_range": 140}`. Spawned by `main.gd._spawn_monsters()` as `scenes/RoamingMonster.tscn` instances — idle until the player is within `chase_range`, then close in and force a battle on contact.

Both reuse `GameState.pending_battle_enemy` + the same deferred `change_scene_to_file` pattern as NPC-triggered battles, so nothing else about the battle system needs to know which of the three trigger types (NPC dialogue, tile chance, monster contact) started it.

### Localization

`scripts/localization.gd` (autoload `Localization`, added right after
`GameState` in `project.godot` so `GameState.locale` is already loaded
by the time it reads it) backs a bilingual English/Traditional-Chinese
UI, following the project's existing "content lives in JSON, not code"
convention:

- `data/locales/en.json` / `data/locales/zh.json` — each
  `{"strings": {...}, "speakers": {...}}`. `Localization.t(key)` looks
  up a UI string (falls back to English, then the key itself, if
  missing); `Localization.speaker(name_en)` translates a dialogue
  speaker's canonical English name via the 8-entry `speakers` table.
- Dialogue JSON (`dialogues/*.json`): every node with body `"text"` and
  every choice can carry an additive `"text_zh"` sibling key (English
  `"text"` is untouched — see `dialogues/elder.json` for the pattern).
  `Localization.text_for(dict, "text")` returns the right one for the
  current locale. **Translation happens at the display layer
  (`dialogue_box.gd`), not in `dialogue_manager.gd`** — the manager only
  cares about flags/branching/battle-triggering, not presentation, so
  it's unchanged; `display_node()`/`_reveal_choices_or_continue()` call
  `Localization.text_for()`/`.speaker()` instead of reading `"text"`/
  `"speaker"` raw. A new dialogue node without `"text_zh"` just silently
  falls back to English — nothing breaks, it's just untranslated.
- `data/npcs/*.json`'s `"name"` field is **not** translated — it's
  write-only (`npc.npc_name` is set but never read anywhere; the
  speaker shown in dialogue comes entirely from the dialogue JSON's own
  `"speaker"` field), confirmed by grepping every script before doing
  the (unnecessary) work of translating it.
- UI screens (`PauseMenu`, `HelpOverlay`, `TitleScreen`, `Battle`) call
  `Localization.t(key)` for their labels/buttons. `PauseMenu` and
  `HelpOverlay` persist for a whole scene's lifetime and can be open
  while the language changes (Options is reachable *from* the pause
  menu), so both connect a `_refresh_texts()` handler to
  `Localization.locale_changed` — one handler per screen, called once
  at `_ready()` too, covers every case (menu open during the change,
  closed, mid-navigation) without scattering refresh calls across each
  button handler. `TitleScreen`/`Battle` only ever exist while
  pause/options (which live inside `Main.tscn`) are *not* open, so they
  just set text once at `_ready()` — no signal needed. `DialogueBox`
  needs neither: `display_node()`/`_reveal_choices_or_continue()`
  already re-run every dialogue turn, so translating inline there picks
  up whatever the current locale is each time automatically.
- **Judgment calls**: the title screen's `"WANDERER'S VILLAGE"` logo
  stays untranslated (a stylized proper noun, not typically translated)
  — only its subtitle/buttons localize. The Options menu's "English"/
  "中文" button labels are proper nouns for the languages themselves,
  never translated either. `locale` is a `GameState` field but
  deliberately **not** reset by `reset_new_game()` — it's a
  player/device preference, not story state, so starting a new game
  doesn't silently revert the player's language choice. Enemy
  `data/enemies/*.json` `"name"` fields (shown via `%s` in battle
  format strings) were left English — the user's ask was scoped to
  dialogue/UI text, not specifically enemy names; a natural follow-up
  if wanted (add them to the `speakers` table) rather than done unasked.
